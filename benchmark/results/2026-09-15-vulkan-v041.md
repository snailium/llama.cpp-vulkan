## Detailed Findings

### Metrics source
Authoritative per-request `timings` JSON scraped from the llama-server `-v` log (`docker logs --timestamps`), deduped against the known 2x echo, then split into tasks by wall-clock window (tasks run sequentially). Aggregates are **weighted** — `sum(prompt_n)/sum(prompt_ms)`, `sum(predicted_n)/sum(predicted_ms)`, `sum(draft_accepted)/sum(draft_n)` — never a mean of rates. Extractor: `benchmark/.v041-run/extract_timings.py`, split: `split_tasks.py` (308 deduped records).
t1/t2/V1-V3 additionally carry client-captured `timings` from the response body; the two agree.

### Cross-generation comparison (v0.4.0 → v0.4.1)
The two stable candidates are **performance-equivalent within run-to-run sampling variance**:

- **Short-context decode** t1 35.8 vs 38.8, t2 38.4 vs 37.8 t/s (±8%, token counts differ by sampling nondeterminism).
- **Agent t4** 17.9 vs 17.8 t/s, acc 0.835 vs 0.820 — effectively identical.
- **Deep-context t3** 5.4 vs 5.6 t/s, acc 0.542 vs 0.553 — identical. The v0.4.0 **deep-context collapse is unchanged in v0.4.1**: this is the known scalar-FA-at-`n_rows==1` path (see `docs/VULKAN-PERF-RESEARCH-20260910.md`, upstream [ggml-org/llama.cpp#28721](https://github.com/ggml-org/llama.cpp/issues/28721)). v0.4.1's small-M matmul work (`6788edb`) does not touch it.
- **t5** decodes at 9.0 t/s here vs 17.6 in v0.4.0, but this is a *workload* difference, not a regression: the agent chose a 74-request path over ECCC's OGC API (v0.4.0 used 4 requests), so it decoded 20,317 tokens into a much deeper context.

### t5 data-source difference (not a regression)
v0.4.1 agent answer **258.6 cm** from Environment & Climate Change Canada `climate-daily` station **OTTAWA INTL A (CLIMATE_IDENTIFIER 6106001)**, field `TOTAL_SNOW`. Reproduced independently by querying `api.weather.gc.ca/collections/climate-daily/items` directly: 318 records, 317 days with `TOTAL_SNOW`, **sum 258.6 cm**, max day 2026-01-15 = 21 cm. The v0.4.0 baseline reported **145.67 cm** from Open-Meteo (ERA5 *reanalysis*, a gridded model that under-reports snow). ECCC station observation is the more authoritative source for an airport total; the run also cross-checked the 21 cm daily max against contemporaneous press reporting. Same task, different (better) source — no unit error.

### Harness observation (not a backend defect)
The first t3 run's session stalled visibly but still delivered a complete 12.7 KB audit: the harness buffers `session.v3.jsonl.zstd` until turn end, so a long single turn looks idle (0.6% container CPU, stale session file) while llama-server runs at 110% CPU. Do not diagnose "hang" from session-file staleness alone; check server CPU and the `/slots` endpoint instead.

That run was also **concurrent with unrelated third-party agent traffic** on the same backend (a `dsh-repeat-tool-breaker` e2e harness repointed onto port 18083). It was therefore discarded and t3 was re-run on an exclusive backend; only the clean re-run's numbers appear above.

### `dsh-repeat-tool-breaker` finding (harness-side, unrelated to the image)
While validating, the v0.4.1 profile's loop guard was found to be **installed and working but structurally evadable**. `dsh --profile headless_lc --dump-config` shows the row present and enabled (`denyAfter: 2` default), and a forced three-times-identical probe is correctly blocked at the 2nd call. However the counter is a *consecutive-run* detector (`st.sig === key ? st.count + 1 : 1`), so an agent that **alternates two variants (A,B,A,B)** resets `st.sig` on every call and never reaches `denyAfter`. An archived stuck session (`session-c20a34d2-…`, preserved at `benchmark/.v041-run/.live.jsonl`) shows exactly this: steps 55-66 alternate `open-data.canada.ca` / `open.canada.ca`, and there are **zero adjacent identical pairs**. Merely varying a cosmetic `description` field defeats it too. Suggested fix: count per signature over a short sliding window rather than only the previous call, and exclude comment-only fields from the identity.
