# XTX: b12182 vs v0.9.0 — +1.3 % decode on t2, and reference-counted checkpoints save no memory

**Date:** 2026-11-12 · **Card:** RX 7900 XTX (Vulkan/RADV) · baseline **v0.9.0**
(`sha256:001928af…`), candidate **dev b12182** (`sha256:e7c736f0…`)

Two targeted comparisons, chosen from the `v0.9.0 → b12182` delta (72 commits, 7 Vulkan):
`da3416d80` (RDNA3/4 large-tile split-K) and `e152332a1` (reference-counted checkpoints).

## Decode: acceptance-controlled, greedy, 3 reps per task

Greedy with a unique per-request salt (without the salt the prompt cache serves whole prompts
and reps collapse to `prompt_n=4`, which silently makes them incomparable).

| task | decode v0.9.0 | decode b12182 | Δ | accept v0.9.0 | accept b12182 |
|---|---|---|---|---|---|
| t1_html | 96.98 | 97.92 | +1.0 % | 75.79 | 77.66 |
| t2_svg | 109.55 | 110.78 | +1.1 % | 90.68 | 90.25 |

Acceptance moved by more than the decode did, so the raw deltas mean nothing on their own.
Regressing decode on acceptance across all six samples per task, image label ignored:

```
t1_html: decode = 0.846 * accept + 32.73   v0.9.0 residuals -0.43/+0.09/+0.15  → median +0.09
                                            b12182  residuals -0.51/-0.02/+0.72  → median -0.02
   net image effect: -0.11 t/s   (nothing)

t2_svg:  decode = 0.848 * accept + 33.16   v0.9.0 residuals -0.51/-0.50/-1.05  → median -0.51
                                            b12182  residuals +0.01/+0.96/+1.09  → median +0.96
   net image effect: +1.46 t/s   (~+1.3 %)
```

The t2 residuals separate cleanly by image (all three baseline below the fit, all three
candidate above); t1 does not. That is consistent with a **per-token** gain from large-tile
split-K on RDNA3 — it shows up where acceptance is already high, so it cannot be explained by
the drafter.

`07ec7c8af` (small-n split-K) is **already in v0.9.0**, so it is not part of this delta.

## Checkpoints: reference-counting did not reduce memory

41-turn growing conversation to ~127k tokens, default `--ctx-checkpoints`, measured from the
container's init PID:

| image | peak host RSS |
|---|---|
| v0.8.0 | 6548 MiB |
| v0.9.0 | 6549 MiB |
| **b12182** (has `e152332a1`) | **6552 MiB** |

Within 4 MiB of each other, and checkpoint-creation throughput is unchanged (same depth:
`prefill_tps` 232.0 vs 231.8, wall 14.3 s both). Reference counting only saves bytes when
checkpoints share identical data; in a monotonically growing conversation every checkpoint
holds a different depth's state, so the retained set is the same size. **The 4.68 GiB plateau
stands.**

The more consequential commit in this delta is `e56f006ed` — *fix on-device state copy sizes for
quantized KV caches*: the element count was computed as `size / ggml_element_size()`, which for
q8_0/q4_0 is a **block** count, so only part of each range was copied ("the restored state was
wrong, or the copy crashed"). Our checkpoints are q8_0/q4_0 on-device copies, so builds before
this fix could restore a wrong state. **No battery task exercises that path**, which is why the
verdict in the archived run does not rest on this build's headline changes.

## Boundaries

- 3 reps per task; enough to separate a 1.3 % effect from the ~4 pp acceptance spread, not
  enough to bound anything smaller.
- Greedy was forced for determinism — a deviation from the battery's "never override sampling",
  scoped to this performance comparison only. The standard battery in
  `benchmark/server-dev-m26.2-b12182-20261107-0518/` used the server's own sampling.
- The depth run used `mmproj` on GPU, which is why VRAM reads 23939 MiB here versus 23087 MiB
  in the earlier checkpoint work.
