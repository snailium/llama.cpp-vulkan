# B70 (Vulkan) A/B: v0.7.0 vs dev b11706 — no gain from the shader-core-count fix

**Date:** 2026-10-23 · **Card:** Intel Arc Pro B70 (BMG G31, 32 GB, `8086:E223`, `xe`)
**Backend:** Vulkan / ANV, Intel ICD pinned, device `Vulkan0`
**Images:** `:latest` = **v0.7.0** (`620d222`) vs **`server-dev-m26.2-b11706-20261017-0340`**
(`sha256:2cdcfafc…`, issue #13) · **Mesa** in image

## Why this pair was tested

Triaging b11594→b11706 (issue #13) left **exactly one** change that reaches a B70 Vulkan
config: `d524bb660` adds `case 0xE223: return 32` to `ggml_vk_intel_shader_core_count()`.
Until then the B70 fell to `default: return 0`, and that zero **gated off** the whole split_k
block (`if (ctx->device->shader_core_count != 0 && …)`) as well as making `prefer_large`
trivially true (`tiles_m > 0 || tiles_l > 0`). With 32, both become real decisions.

So the expected signal is in **prefill** (mulmat dispatch), not decode.

Config: the B70 golden, translated to Vulkan — ctx 131072, KV **q8_0/q8_0** both sides,
MTP3 (`draft-mtp`, `n_max=3`, `p_min=0.1`, draft KV q8_0/q8_0), FA on, `ngl 999`, np 1,
**`MMPROJ_OFFLOAD=true`**. Sampling was **not** overridden; the server-side golden values
(temp 0.7 / top_p 0.80 / top_k 20 / presence 1.5) applied.

## Prefill — the measurement that matters. No gain.

Fixed English filler, `max_tokens 24`, `temperature 0`, ascending depth so a cached prefix
cannot be mistaken for a shallower prompt. `prompt_per_second` straight from the server.

| prompt_n | v0.7.0 tok/s | b11706 tok/s | Δ |
|---|---|---|---|
| 1315 | 368.98 | 366.01 | **−0.8 %** |
| 4063 | 546.45 | 543.97 | **−0.45 %** |
| 10192 | 352.45 | 345.93 | **−1.85 %** |

**Dev is marginally slower at every depth.** The change is real at the code level — the
gate genuinely flips — but it does not buy anything measurable here, and the direction is
slightly negative.

A plausible mechanism for the small regression: with `shader_core_count == 0`, `prefer_large`
evaluated to *true* unconditionally, so the dispatcher always took the large-tile path. With
32 it becomes a real comparison that sometimes declines large tiles. That is a behaviour
change, not obviously a speed-up.

## Task battery — differences track acceptance, not the image

Same prompts, same sampling, `prompt_n` **identical** across images on every task (43/43,
32/32, 3528/3528, 1064/1064, 4160/4160), so the comparison is like-for-like.

| task | decode v0.7.0 | decode b11706 | Δ | accept v0.7.0 | accept b11706 |
|---|---|---|---|---|---|
| t1_html | 45.78 | 44.14 | −3.6 % | 82.79 | 79.20 |
| t2_svg | 48.90 | 47.06 | −3.8 % | 90.50 | 87.28 |
| v1 | 31.32 | 29.64 | −5.4 % | 64.02 | 60.40 |
| v2 | 34.25 | 34.07 | −0.5 % | 56.65 | 56.98 |
| v3 | 28.29 | 28.35 | +0.2 % | 57.30 | 58.81 |

Every decode delta is the same sign and roughly the same magnitude as its acceptance-rate
delta, and sampling runs at temp 0.7, so **n=1 per task cannot separate the images**.
Wall clock follows the same pattern (t1 33.92→35.25 s, v1 39.50→41.08 s, v3 41.70→40.84 s).

**Read as: no regression established, no improvement established.**

## Vision projector was on the card

`MMPROJ_OFFLOAD=true`, and the timing confirms it: v1 carries 3528 prompt tokens and took
39.5 s wall **including** ~22 s of decoding, leaving ~17 s for prefill + image encode ≈
**207 tok/s**. The documented CPU-encoder baseline for this same task shape is **49.95 tok/s**,
so this is unambiguously GPU. (The `CLIP using …` log line only prints under `-v`, which was
not enabled; the inference above is the substitute the B70 skill prescribes.)

## New pitfall found: the Vulkan image does not pin the listen port

`b11706` **and** v0.7.0 both default to `--port 9931` (upstream #30159, landed b11540), and
the Vulkan image — unlike the SYCL image, whose Dockerfile sets `ENV LLAMA_ARG_PORT=8080` —
does not pin it. An ad-hoc `docker run` without `-e LLAMA_ARG_PORT=8080` therefore publishes
8080 → nothing, logs `listening on http://0.0.0.0:9931`, and every probe is
`ConnectionResetError`. Production is unaffected because the compose passes the variable.

This cost a full A/B round here: the first run reported connection resets on **both** images
while the health loop silently expired. The runner now aborts loudly and prints the
`listening on` line instead of proceeding.

## Verdict

**The dev image is not worth adopting for the B70 Vulkan route.** Its single B70-relevant
change is behaviourally real but not an improvement (prefill −0.45 % to −1.85 %, all deltas
inside noise), and everything else in the range is either AMD/x86-only, RDNA4-only, or does
not reach `qwen35`.

Nothing here argues against keeping production on v0.7.0 (`620d222`).
