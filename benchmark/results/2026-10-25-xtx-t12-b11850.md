# T1/T2 performance A/B on the XTX: v0.7.0 vs b11850 — no difference, and the one apparent regression is acceptance noise

**Date:** 2026-10-25 · **Card:** RX 7900 XTX (Vulkan/RADV) · Issue #14 candidate
**Images:** `:latest` = v0.7.0 (`620d222`) vs `server-dev-m26.2-b11850-20261024-0355`
**Config:** production — Qwen3.8-27B-Q4_K_M, ctx 131072, KV q8_0/q4_0, MTP4 (`p_min 0.1`),
mmproj on GPU, `n_gl 999`, np 1. Greedy (`temperature 0`, `top_k 1`), 3 reps per task.

## Method note: the first run was contaminated by the prefix cache

Without a per-request salt, reps 1 and 2 came back with **`prompt_n = 4`** instead of 43/32 —
the prompt cache served the whole prefix, so those reps were not comparable to rep 0. Every
number below comes from a **second run with a unique `[rN-<random>]` prefix per request**,
which forces a full prefill each time (`prompt_n` 41–54 on every sample).

The same first run also produced *different* output on identical greedy prompts across reps.
That is a property of this speculative config (`p_min 0.1` samples proposals), not of the
image, and the salted run makes it moot by giving each rep a genuinely different prompt.

## Result

Medians over 3 reps:

| task | decode base | decode dev | Δ | accept base | accept dev | Δ | TTFT base | TTFT dev | Δ |
|---|---|---|---|---|---|---|---|---|---|
| t1_html | 101.65 t/s | 97.99 t/s | **−3.6 %** | 80.70 % | 76.78 % | −3.92 pp | 0.262 s | 0.262 s | 0 % |
| t2_svg | 111.95 t/s | 112.41 t/s | **+0.4 %** | 91.76 % | 92.04 % | +0.28 pp | 0.253 s | 0.259 s | +2.4 % |

Taken alone, the t1 row looks like a regression. It is not, and the data says why.

## Decode speed is a deterministic function of acceptance rate here

Regression across all 6 samples per task, ignoring which image produced them:

```
t1_html:  decode = 1.102 x acceptance + 12.65     residuals -0.85 .. +0.70 t/s
t2_svg:   decode = 1.096 x acceptance + 11.36     residuals -0.25 .. +0.22 t/s
```

**The image label adds nothing.** Residuals interleave with no sign pattern:

| task | v0.7.0 residuals | b11850 residuals |
|---|---|---|
| t1_html | +0.04, −0.22, +0.03 | −0.85, +0.30, +0.70 |
| t2_svg | +0.05, −0.06, −0.25 | +0.22, +0.20, −0.16 |

The mechanism is straightforward: each accepted draft token removes a target forward pass, so
+1 pp acceptance is worth **~1.1 t/s** at this acceptance level. The t1 "regression" is a
−3.92 pp acceptance fluctuation (same config, only a random salt differed) multiplied by that
slope. t2's acceptance barely moved, and its decode barely moved — as the model predicts.

**Conclusion: v0.7.0 and b11850 are indistinguishable in T1/T2 performance.** TTFT is flat
(0 % and +2.4 %, both within the 0.25–0.26 s measurement floor), decode differences are fully
explained by acceptance variance, and T1/T2 prompts are 43/32 tokens so prefill throughput is
meaningless here.

## Cross-check against the earlier byte-identical smoke

The smoke on 3 prompts found **identical SHA-256 output** on both images, with `draft_n`
identical (688/280/100) and decode within 0.4 %. The load path also matched (free VRAM 720 vs
730 MiB). That the T1/T2 accept rates move but the images never differ is consistent: what
varies is the sampling path, not the graph.

## Verdict

**No reason to promote b11850.** Its only our-model change is `839a572a4` (qwen35 output
reshape, a merged-reshape refactor) which the smoke proved byte-identical, and T1/T2
performance is identical once acceptance is controlled for. Production stays on **v0.7.0
(`620d222`)**.

## Honest boundaries

1. **3 reps per task.** Enough to expose the acceptance-driven spread (~4 pp) and show the
   image term is smaller than it, not enough to bound a <1 % effect precisely.
2. **Greedy was forced for determinism**, which is a deviation from the battery's "never
   override sampling" rule; that rule protects quality measurements, and this is a
   performance comparison where determinism is the instrument.
3. **T1/T2 only, as asked.** No agentic or vision tasks, and no long-context measurement;
   graph-shape changes could in principle matter at depth, though nothing here suggests it.
4. **The acceptance rates are not quality signals.** They measure how well the MTP drafter
   predicts the target, which varies with prompt content (and here, with the salt).
