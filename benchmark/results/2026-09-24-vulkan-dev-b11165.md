## 5. Findings

### 5.1 ⚠️ `GOLDEN-CONFIG.md` §4 B70 config cannot serve vision (real, actionable)

The B70 golden config **omits `--mmproj`** while the XTX config includes it. With
that config the first V1 request failed:

```
W srv operator(): got exception: {"error":{"code":500,"message":
  "image input is not supported - hint: if this is unexpected, you may need to provide the mmproj",
  "type":"server_error"}}
```

and `/props` reported `modalities: {'vision': False, ...}`.

**Adding `--mmproj … --no-mmproj-offload` fixed it** — `modalities.vision` became
`True` and all three vision tasks passed. The B70 results in §4 are from that
corrected launch; load size and free VRAM were unchanged (mmproj stays on the host
with `--no-mmproj-offload`).

**Recommendation:** add `--mmproj /models/mmproj-Qwen3.8-27B-Q8_0.gguf
--no-mmproj-offload --image-min-tokens 1024` to the B70 block in
`GOLDEN-CONFIG.md` §4. Until then the documented B70 config is text-only.

### 5.2 Harness/system notes (not backend defects)

1. **Orphaned `docker run` wrappers.** After a harness task ends, its
   `run_agent_task*.sh` shell can linger in `do_wait` with the container already
   gone, and the log gains no `rc=` line. This cost real time — twice I read it as
   "task hung/failed" when the task had in fact completed or was still running.
   **Lesson: identify harness containers by image (`docker ps | grep dsh-container`),
   never by name** — they are named randomly (`competent_brown`, `dreamy_snyder`).
2. **The harness container reports `(unhealthy)` the whole time while working
   normally.** Container healthcheck state is meaningless here (documented in
   `backend-test-suite`; confirmed again).
3. `ERR_PNPM_IGNORED_BUILDS` (opencli build script blocked) — expected, harmless.
4. A harness task at 65 K context consumed a **8310 MiB prompt-state checkpoint
   exceeding the 8192 MiB cache limit** (`alloc: - prompt state size … exceeds cache
   size limit, skipping`) — a checkpoint was skipped, no failure. Worth knowing at
   deep context.

### 5.3 t5 snowfall — two different, internally-consistent answers

| Card | Answer | Months summed |
|---|---|---|
| XTX | **217.0 cm** | Nov 32.5 + Dec 54.6 + Jan 81.6 + Feb 48.3 |
| B70 | **258.6 cm** | those four **+ Mar 41.0 + Apr 0.6** |

Both are arithmetically correct **for the month set each chose**; the B70 also
cross-checked against a third-party seasonal total. The task's window
(2025-11-01 → **2026-12-31**) plainly *includes* March and April 2026, which favours
the B70 reading of the range — but the XTX explicitly flagged the ambiguity and
also offered "258 cm" as the seasonal figure. **This task is ambiguous as written
and both answers are defensible**; it is not evidence of a backend defect, and the
prior baseline (2026-09-16) failed t5 outright on *both* cards. Both cards pass it now.

### 5.4 t4 GPU identification — model hallucination on XTX only

| Card | Reported AMD GPU | Truth (`lspci`) |
|---|---|---|
| XTX | "Radeon RX **6600** (0x744c, Navi 10)" | `1002:744c` = **Navi 31, RX 7900 XTX** |
| B70 | "Radeon RX 7900 XT/XTX/GRE (Navi 31)… 24 GB indicates **XTX**" | correct |

The XTX run inverted the device id: `0x744c` **is** the value it printed, but it
mapped it to the wrong product name. The B70 run reasoned correctly from the same
PCI id. Everything else in both JSON outputs (CPU Ryzen 7 5700X, 30 GiB RAM,
nvme0n1 465.8 GB + nvme1n1 476.9 GB, partitions) matched the host exactly.
**Both still PASS** — the field is wrong, the document is valid — but a model-quality
difference between cards, not a backend one, and worth noting.

### ⚠️ Router restore — the breaker tripped, twice, on both cards

Per the skills, `/health` ok is **not** proof the platform is restored. Both runs
reproduced the failure:

| After restoring | worker `/health` | worker infers? | `/workers` | routed request |
|---|---|---|---|---|
| `xtx-vulkan` | `{"status":"ok"}` | yes | `is_healthy: false, status: failed` | **503 `no_available_workers`** |
| `b70-sycl` | `{"status":"ok"}` | yes | `is_healthy: false, status: failed` | (503 pattern) |

Fix applied both times: **`docker restart smg`** → workers re-registered in ~30-40 s
→ `/workers` showed `is_healthy: true, status: ready` for **both** → the routed
request then returned a real completion with `HTTP 200`.

**Final state (verified):**

```
http://192.168.111.101:18080  healthy= True  status= ready    (b70-sycl)
http://192.168.111.101:18090  healthy= True  status= ready    (xtx-vulkan)
routed request via :40114 -> 200, content "ok"
```

**Both production containers are up and serving, and the platform is verified
end-to-end through the router, not merely via `/health`.**
